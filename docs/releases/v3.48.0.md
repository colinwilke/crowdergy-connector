# v3.48.0 — checking that a command actually took effect

Until this release the connector answered only one question after
writing a control value: *is my value in the entity?* That is not the
same question as *did my command work*, and two field cases showed how
far apart the two can be. Both ran silently for months.

**A configured value the entity cannot hold.** A heating device had
`value_off = 35` mapped against an entity whose range ends at 30. Every
write was clamped to 30 — the device could never reach the commanded
state — and that only ever appeared as a log warning nobody reads.
Worse, the comparison still expected 35, so the entity looked
permanently "drifted" no matter what. The AUTO hold loop read its own
clamp as a human turning the dial, decided it should not overrule a
person, and paused control of the device for two hours. Repeatedly.

**A value the device accepts and then ignores.** A Stiebel heat pump in
programme mode keeps two domestic-hot-water setpoints, comfort and eco,
and follows whichever the current time window selects. Crowdergy writes
the comfort register; it wrote 35 °C and the register held 35 °C, while
the pump ran its eco register at 49.5 °C the whole time. The tank never
came down. Nothing anywhere reported a problem, because from the
connector's point of view the write had succeeded.

## What changed

**Comparisons now use the value that was actually written.** The clamp
and the comparison are one unit: the hold loop, the idempotency guard
and the `is_on` / `cool_on` read-back all clamp before comparing. A
value outside the entity's range no longer manufactures drift, and the
override detection stops firing on the connector's own doing.

One case deserved an explicit answer rather than a guess: if the on- and
off-values clamp to the *same* number, the two states are no longer
distinguishable at the device, so the connector reports "unknown"
instead of picking the first match.

**Two new states reach the app.** `control_value_rejected` says the
configured switching value lies outside what the entity accepts.
`control_ineffective` says the value is sitting correctly in its entity
while the device runs a different setpoint. Both appear under "currently
active" with the concrete next step, and both clear themselves.

**A new optional mapping, the same one for every controllable device
type:** *setpoint the device actually runs*. It is read-only — the
connector never writes to it, it only compares. Stiebel ISG exposes it
as `sensor.<hp>_target_temperature_water` and
`sensor.<hp>_target_temperature_hk_1`. Leave it empty and nothing
changes: without a reference point there is no statement to make, and
the connector does not invent one.

A mismatch is only reported once it has persisted for 15 minutes — a
device is allowed to ramp and to take its time. An unreadable sensor
clears the clock rather than claiming a control fault.

## Upgrading

Requires the matching backend release, which is already deployed. No
re-provisioning: the new mapping is optional and appears the next time
you edit a device.
