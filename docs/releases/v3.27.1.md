## v3.27.1 — Telemetry-Resilienz + proaktives Token-Refresh

Robustness-Release auf v3.27.0. Rein interne Zuverlässigkeits-
Verbesserungen — keine neuen Config-Felder, kein neuer API-/Slot-Surface,
keine Breaking Changes. Bestehende Pairings/Geräte/Presets unberührt.

### Verbessert

- **Telemetry-PATCH Retry/Backoff (Backlog #18):** Der Telemetrie-Push
  (primärer Tick-Send *und* der Idle-Mirror) läuft jetzt über
  `_patch_telemetry_with_retry` mit kurzem, bounded Retry/Backoff
  (3 Versuche, 0.5 → 1.0 s) auf **transiente** Fehler — Transport-Fehler
  (Netzwerk-Flap) sowie HTTP 5xx/429. **Permanente** 4xx inklusive der
  404/410-Device-Eviction gehen ohne Retry durch (kein Endlos-Loop auf
  backend-seitig gelöschte Geräte). Vorher ging ein Send bei einem
  transienten Blip verloren und wurde erst beim nächsten
  Soft-Heartbeat-Tick (bis zu 90 s später) wiederholt — was iOS-Tiles
  unnötig auf „stale" flippen ließ. kWh war und bleibt dabei verlustfrei
  (das Δ wird gegen den letzten **erfolgreich** gesendeten Stand
  gerechnet).
- **Proaktives Token-Refresh (Backlog #19):** Das Access-Token wird
  ~120 s vor seinem Ablauf proaktiv erneuert, statt erst reaktiv auf
  einen 401 zu warten. Der `exp`-Claim wird dafür unverifiziert aus dem
  JWT gelesen (nur fürs Scheduling), der Refresh ist single-flight über
  den bestehenden `seen_token`-CAS-Lock (keine parallelen
  `/auth/refresh`-Calls → keine Refresh-Token-Rotation-Kaskade). Der
  reaktive 401-Pfad bleibt als Fallback erhalten (u. a. für Tokens ohne
  dekodierbares `exp`).

### Kompatibilität
