# v3.48.2 — profiles never hijack another device's control, AI-off survives a dropped connection

Two safety fixes. Both concern control slots, which switch real hardware.

## Profile prefill no longer guesses control entities

When you pick a community profile, its entity IDs come from the contributor's
installation and are resolved against yours. For an entity without a registry
identity (typically a helper such as `input_select.*_lademodus`), the resolver
fell back to matching the end of the name. A battery profile could therefore
suggest the charge-mode helper of your **wallbox** for the battery's control
slot — one click on "Next" and battery commands would have switched the wallbox.

Now:

- Control slots and `input_*` helpers are never resolved by name suffix. They
  resolve only by exact ID or a unique registry identity.
- A control slot is never prefilled with an entity another Crowdergy device
  already controls — not even on an exact ID match.
- Slots that cannot be resolved stay empty instead of showing the
  contributor's non-existent entity ID. A helper that still has to be created
  keeps its ID as the creation hint.

Read-only slots keep the suffix fallback for older profiles.

## AI-off handover also runs when the off-frame was missed

Turning Crowdergy AI off (per device or via the emergency stop) sends an
`is_active=false` frame; the integration then hands the device back: battery
to passive, charge-mode hold cancelled, heating/hot water to its off value. If
the connection was down at that moment, the frame never arrived. The 90 s
state resync updated the cached flag but skipped the device, so the
charge-mode hold kept re-writing the last AI command until its lease expired.

The resync now runs the same handover when the backend reports a device as
off that was on locally. It never does so on startup for devices that were
already off, so a Home Assistant restart writes nothing.

## Upgrading

No schema, entry-data or backend-contract change; no re-provisioning.
