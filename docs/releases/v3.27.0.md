## v3.27.0 — Connector-Pairing-Alias + iOS-Preset-Apply (value_map on device_update)

Additives Feature-Release auf v3.26.0. Keine Breaking Changes für
normale HACS-Installationen.

### Neu

- **`/connector/*`-Pairing-Alias (Backlog #39, Backend-Seite):** Das
  Backend bietet `POST /api/v1/connector/pairing-code` +
  `/connector/claim` als Alias zu `/box/*` an (gleiche Shapes), damit
  der HACS-Connector künftig denselben 8-stelligen Code-Pairing-Flow
  nutzen kann wie die Box. **In diesem Release nur die
  Backend-Endpoints**; die Connector-seitige Onboarding-Umstellung
  (Picker statt URL+Long-Lived-Token) folgt separat. `/box/*` bleibt
  funktional.
- **Preset-Apply on `device_update` (Backlog #40):** Wenn ein User im
  iOS-Preset-Picker ein Vendor-Preset auf ein Gerät anwendet, stempelt
  das Backend das Profil und broadcastet einen `type=device_update`-
  SSE-Frame. Der Connector zieht daraufhin das Gerät (vendor/model) +
  das Preset aus dem Store und merged den **vollen `value_map`** —
  insbesondere die Batterie-Modi (`value_battery_mode_active/passive`),
  die das Backend bewusst NICHT 1:1 schreibt — verbatim in die lokale
  Device-Config (Default-DENY auf `PRESET_VALUE_SLOTS`), gefolgt von
  einem entkoppelten Config-Reload. Damit wirkt ein iOS-Preset-Apply
  end-to-end bis in die HA-Steuer-Slots. NIE stumm — der iOS-Apply IST
  die User-Bestätigung; das Ganze sitzt hinter dem
  Remote-Control-Consent-Gate.

### Kompatibilität

- Rein additiv: neuer SSE-Frame-Typ (`device_update`) + neue
  Backend-Endpoints. Bestehende Pairings/Geräte unberührt.
- Setzt backend-seitig die `apply-preset`-Migration (`20260615_0001`:
  `devices.vendor/model/crowd_preset_updated_at`) + den
  `POST /devices/{id}/apply-preset`-Endpoint voraus, damit
  `device_update` vendor/model trägt.
- Box: Vendor-Pin nach diesem Release auf v3.27.0 bumpen
  (Backlog #27-Regressionstest in der Alpha geparkt).
